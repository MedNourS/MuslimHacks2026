# frontend

Generated by `create-fronton` — Vite + React 19 + TypeScript + Tailwind v4, opinionated by default.

## Getting started

```
bun install
bun run dev
```

## What's already wired in

- **Tailwind class obfuscation** (`obfuscateTailwind()` from `@mednours/fronton`, in
  `vite.config.ts`) — production builds only (`bun run dev` stays fully readable). After
  Tailwind's CSS and the JS bundle are both fully built, every real Tailwind utility class gets
  hashed to a short opaque name (`bg-red-500` → something like `f3a91c2`) in both the stylesheet
  and the built JS/HTML — shrinks output a bit further than minification alone, and makes the
  Tailwind usage non-obvious from devtools. It rewrites `className`/`class` values directly,
  including through `clsx()`-style calls, even after those get renamed by minification (see the
  plugin's own source comments for why that specific case matters). What it can't reach: a class
  list built at runtime from an array/object with no literal strings in scope, or a template
  literal with real `${}` interpolation — those are left exactly as-is rather than guessed at. Turn
  it off entirely with `obfuscateTailwind({ enabled: false })` if you'd rather ship readable class
  names (e.g. classes referenced by an end-to-end test suite or an external stylesheet — or use
  `safelist` to exempt just those).
- **Gzip + Brotli compression** (`frontonCompression()`) — both algorithms, every production build,
  running after obfuscation so the compressed files reflect the hashed output. Skips tiny files
  (under 1 KiB by default) where compressing doesn't pay for itself.
- **SEO / social preview meta tags** (`index.html`) — title, description, and the full Open Graph +
  Twitter card block, prefilled from the project name and the description given at scaffold time.
  Add a real `public/og-image.png` (1200x630) when you have one; `og:image`/`twitter:image` already
  point at it. `og:url` and a Twitter handle are left out on purpose — neither is known yet.

`@mednours/fronton` (the root import, used in `vite.config.ts`) and `@mednours/fronton/client`
(used in application code, like `src/App.tsx`) are separate entry points on purpose — the root one
pulls in Node-only build tooling that has no business in a browser bundle, so anything meant to be
called from your components (right now, just `resolveApiBaseUrl()`) is kept on the `/client` path
instead, with nothing else attached to it. There's a third, `@mednours/fronton/motion`, for the
`lazyDomAnimation()`/`lazyDomMax()` animation loaders — it needs `bun add motion` first, which is
why it's kept off `/client`: importing an entry point should never oblige you to install
something.
## Backend

A backon backend was found at `../backend` while this project was scaffolded, so
`vite.config.ts` already proxies `/api` to it during `bun run dev` (see `server.proxy`, backed by
`backonProxy()` from `@mednours/fronton`) — no CORS setup or hardcoded port needed locally. In
production, set `VITE_API_BASE_URL` if the frontend and backend deploy to different origins;
leave it unset for same-origin deployments.

### Typed API client

```
bun run sync-api
```

Regenerates the backend's typed client (`bun run generate-client` over there) and copies it here as
`src/lib/api.ts` — one function per mounted route, so calling the API is `usersApi.getUser(id)`
rather than a hand-written `fetch` you have to keep in step with the backend. Re-run it whenever
routes change on the backend.

Three things are rewritten on the way across, because backon generates that file for Node and this
is a browser bundle: its `process.env.API_BASE_URL` lookup becomes `resolveApiBaseUrl()` (in a Vite
bundle `process` doesn't exist, and the original falls through to `""` silently rather than
failing); the base URL picks up the `/api` prefix in dev, since the generated paths are the
backend's real ones and it's the proxy that owns that prefix — without it requests miss the proxy
entirely and Vite answers with `index.html`; and an unused `import type { z } from "zod"` is
dropped, since it would otherwise fail `bun run typecheck` on a project that has no reason to
install zod.

`src/lib/api.ts` is committed, not gitignored: a deploy builds this project alone, with no backend
checkout beside it to regenerate from.


## Routing

react-router, with the route table in `src/routes.tsx` and page components in `src/pages/`. To add
one:

```
bun run add-page about          # -> src/pages/About.tsx at /about
bun run add-page users/:id      # -> src/pages/UsersId.tsx at /users/:id
```

That writes the component and inserts its lazy import and route entry into `src/routes.tsx` at the
`fronton:pages` / `fronton:routes` markers, above the catch-all. Adding one by hand is fine too —
copy the shape of an existing entry, and keep the `lazy()` wrapper.

Every page is lazy-loaded, so a first visit downloads only the route it landed on rather than the
whole app. That's worth preserving as the app grows; it's the biggest single lever on load time
here, and the easiest to lose by adding a plain import.

Pages can call the backend through `src/lib/api.ts` once you've run `bun run sync-api` — see the
Backend section above.


## Installable app (PWA)

This project was scaffolded with PWA support, via
[vite-plugin-pwa](https://vite-pwa-org.netlify.app/). `bun run build` emits a service worker and a
web manifest alongside the normal output, which makes the app installable from the browser — no
extra setup.

The service worker only runs in a production build. To try it locally:

```
bun run build
bun run preview
```

Two things to change before shipping: swap `public/icon-192.png` and `public/icon-512.png` for
real artwork (they're solid-color placeholders, sized so the install prompt accepts them), and
adjust `name`/`theme_color` in the `VitePWA` manifest in `vite.config.ts` if the defaults taken
from the project name aren't what you want.

Updates use `registerType: "prompt"` rather than `"autoUpdate"`: a new version waits instead of
reloading the page under someone mid-task. Nothing surfaces that prompt yet — wire it up when you
want it:

```ts
import { registerSW } from "virtual:pwa-register";

const updateSW = registerSW({
  onNeedRefresh() {
    // show your own "a new version is available" UI, then:
    // updateSW(true);
  },
});
```

Precaching covers the built app shell (JS, CSS, HTML, icons, fonts) and nothing else. API responses
are deliberately not cached — the right policy depends on your data, and a wrong one serves stale
responses with no obvious cause. Add a `workbox.runtimeCaching` rule in `vite.config.ts` when you
know what you want.


## Deploying

`vercel.json` pins `bun install`/`bun run build` as the install/build commands — connect the repo
at [vercel.com/new](https://vercel.com/new) or run `vercel deploy`; Vite's static output needs
nothing else.

## Requirements

Bun >= 1.3.
